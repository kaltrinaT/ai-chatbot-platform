# Security

This document explains how the AI Chatbot Platform handles client credentials, what is stored, what guarantees exist, and the known limitations of the current security model.

---

## Credential Inventory

### AWS

| Field | Stored | Format | Used for |
|---|---|---|---|
| `deploymentRoleArn` | Yes | Plaintext | STS AssumeRole during onboarding and deployment |
| `sts:ExternalId` | Derived (the tenant's ID) | Plaintext, not a secret | Sent on every AssumeRole; the client's trust policy conditions on it so the role serves one tenant only |

## Encryption at Rest

All secret values are encrypted using AES-256-GCM before being written to the database. The implementation is in [`src/lib/crypto.ts`](src/lib/crypto.ts).

- **Algorithm:** AES-256-GCM
- **Key length:** 256 bits (32 bytes), supplied via `PLATFORM_ENCRYPTION_KEY` environment variable
- **IV:** 12-byte random value generated per encryption call
- **Authentication:** GCM auth tag is stored alongside the ciphertext — tampered ciphertext will fail to decrypt

The stored format is `iv_hex:auth_tag_hex:ciphertext_hex`. No raw secret value is ever written to the database.

The encryption key must be set as an environment variable and must **not** be stored in the database or committed to source control.

### Retention after a tenant is deleted

A deleted tenant's row is kept, soft-deleted, as the audit trail. That covers its deployments, who triggered them, and which AWS account or Azure subscription they targeted. Its **secrets are erased**. When a teardown succeeds, the same update that sets `deleted_at` also sets `llm_api_key_encrypted`, `pinecone_api_key_encrypted`, `docs_signer_secret_encrypted` and `docs_signer_url` to `NULL` ([`src/lib/tenantErasure.ts`](src/lib/tenantErasure.ts)).

| Question | Answer |
|---|---|
| Why erase rather than soft-delete the secrets? | They have no remaining purpose. The docs-signer they authenticated is destroyed, a deleted tenant cannot be redeployed, and a returning customer onboards as a new tenant. Keeping them would only leave every former customer's keys recoverable by anyone holding the database and `PLATFORM_ENCRYPTION_KEY`. Erasure follows GDPR Art. 5(1)(c) and (e), data minimisation and storage limitation, and mirrors the AWS teardown, which force-deletes the customer-side copies in Secrets Manager. |
| Why only on success? | The Azure teardown needs the customer's Pinecone key to delete the index. Erasing on request would make a failed teardown impossible to retry, so a failed or cancelled destroy leaves every secret in place. |
| What if the success webhook is lost? | Reconciliation from the GitHub run ([`src/lib/reconcile.ts`](src/lib/reconcile.ts)) applies the same erasure, so a lost webhook cannot leave secrets behind. |
| What is kept? | Identifiers, not credentials: secret ARNs (of since-deleted secrets), account, subscription, tenant and client IDs, and the slug. |
| Is the erasure immediate everywhere? | No. The database's point-in-time restore keeps history for 6 hours (the Neon project's `history_retention_seconds`), so erased ciphertext stays recoverable from history for up to that long. Still encrypted, it is readable only together with `PLATFORM_ENCRYPTION_KEY`. |

**Not done: crypto-shredding.** Encrypting each tenant's secrets under its own data key, and destroying that key on deletion, would make erasure immediate in backups too. With a 6-hour retention window the added key management is not yet worth it. It becomes worthwhile if backups are ever kept longer.

## AWS Security Model

Figures: [before](docs/figures/fig-20-aws-credential-model-before.svg) · [after](docs/figures/fig-21-aws-credential-model-after.svg)

### How it works

The client's deployment role carries **two trust statements**, because two different callers need it and they prove themselves in different ways.

| Caller | Action | Proof | Used for |
|---|---|---|---|
| GitHub Actions | `sts:AssumeRoleWithWebIdentity` | An OIDC token GitHub signs, naming this tenant's environment | Every deploy, teardown and connection check |
| The platform itself | `sts:AssumeRole` | The platform's AWS account, plus this tenant's `sts:ExternalId` | Onboarding only — writing the tenant's API keys into their Secrets Manager |

**Deploys and teardowns** involve the platform's AWS account not at all. GitHub signs a token describing the workflow run, AWS validates it against the GitHub OIDC provider *in the client's own account*, and STS issues credentials that live only for the run. Nothing reusable exists in the platform database, in GitHub, or in the workflow's inputs.

**Onboarding** is the one thing GitHub cannot do. Before any workflow exists, the platform writes the tenant's LLM key, vector-database key and document-signing secret straight into the client's Secrets Manager, with 15-minute credentials used in memory and then discarded. This is what keeps those values out of GitHub Actions entirely — only the resulting ARNs are ever sent to a workflow, which is a property the Azure path cannot offer, since Azure has no secret store until Terraform creates one.

Both statements are created by [`infra/bootstrap/aws/tenant-bootstrap.yaml`](infra/bootstrap/aws/tenant-bootstrap.yaml), which the client applies from a CloudFormation Quick Create link the wizard builds.

### Why clients retain control

The IAM role is created and owned by the client, in their account, from a template they review before creating anything. Deployments cannot authenticate unless:

1. The client's account has GitHub registered as an OIDC identity provider.
2. The role's trust policy admits the exact subject this tenant's workflow runs present.
3. The role has not been deleted or had its trust policy changed.

Deleting the bootstrap stack removes the role and, with it, all access — no action is needed on the platform side, and the platform cannot prevent it.

### Why the subject names the tenant

The subject is what keeps one client's trust from covering another's. A ref-based subject (`repo:OWNER/REPO:ref:refs/heads/main`) would be *identical for every client*, so any tenant's deploy could assume any role that trusts this repository — and an operator who typed someone else's role ARN into the wizard would provision into a stranger's account.

Running each job in a GitHub environment named after the tenant puts the tenant into the token instead:

```
repo:OWNER/REPO:environment:tenant-<tenant-uuid>
```

Every other tenant's runs carry a different subject and are refused by AWS, not by a check inside the platform. The trust policy matches with `StringEquals`, never `StringLike`: a wildcard anywhere in that subject would readmit every other tenant. This is the same mechanism the Azure path uses, built by the same function — see [`src/lib/githubOidc.ts`](src/lib/githubOidc.ts).

GitHub offers no way to put an arbitrary per-run value into the claim, so the environment is the mechanism rather than a preference. **Private repositories need GitHub Pro, Team or Enterprise for environments.** Without one this fails closed: the token carries no environment, no client's trust matches, and nothing deploys.

### Why the ExternalId still exists

The onboarding statement is the only place the platform's account is trusted, and it is only safe because of `sts:ExternalId`.

Trusting the platform's account alone is trust in the platform *as a whole*: the role cannot tell which tenant a request is being made for. Anyone who reaches the onboarding form and knows a role ARN — not a secret, and the required `chatbot-client-deploy-` prefix makes it guessable — could otherwise have the platform write into an account that is not theirs. This is the [confused deputy problem](https://docs.aws.amazon.com/IAM/latest/UserGuide/confused-deputy.html).

The `ExternalId` is **the tenant's own ID** (see [`src/lib/awsTrust.ts`](src/lib/awsTrust.ts)). A trust policy conditioned on it accepts calls for that tenant and refuses every other, and STS enforces this, not the platform. The value is issued by the platform when the onboarding wizard opens, never typed by whoever fills in the form — otherwise an attacker would simply enter the victim's value. It is not a secret: it is expected to appear in the client's policy and in CloudTrail.

A single platform-wide ExternalId would not work. Every client's policy would carry the same value, so a tenant created against someone else's role would send it too.

### Independent verification via CloudTrail

Every `sts:AssumeRole` call and every subsequent API call made under those temporary credentials is recorded in the client's own AWS CloudTrail. The platform cannot suppress or alter these logs. Clients can verify platform activity by filtering CloudTrail for:

- **Event name:** `AssumeRoleWithWebIdentity` (deploys, teardowns, checks) or `AssumeRole` (onboarding)
- **Session name pattern:** `deploy-{slug}-*`, `destroy-{slug}-*`, `verify-{slug}-*`, or `tenant-onboarding-{slug}`
- **`requestParameters.externalId`:** on onboarding calls, the tenant the call was made for

A federated call additionally records the token's subject, so the client can confirm from their own logs that each deployment carried the environment belonging to the chatbot it claimed to be for.

This means clients do not need to trust the platform operator's claims — they can independently audit every action taken in their account.

### Recommended trust policy

[`infra/bootstrap/aws/tenant-bootstrap.yaml`](infra/bootstrap/aws/tenant-bootstrap.yaml) creates exactly this, and the wizard also shows it filled in for a client who prefers to apply it by hand. Apply it **before** submitting the form, since onboarding writes the tenant's secrets immediately:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "GitHubActionsDeploy",
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::CLIENT_ACCOUNT_ID:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:OWNER/REPO:environment:tenant-TENANT_ID"
        }
      }
    },
    {
      "Sid": "PlatformOnboarding",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::PLATFORM_ACCOUNT_ID:root"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "TENANT_ID_SHOWN_IN_THE_WIZARD"
        }
      }
    }
  ]
}
```

Each condition is what limits its statement to one chatbot. Without the subject condition the role would be assumable by any tenant's deployment; without the ExternalId condition it would be assumable for any tenant the platform is asked to create.

**Tenants onboarded before this changed must re-run the bootstrap.** Their roles trust the platform account for deploys, which the deploy workflow no longer uses, so their next deploy fails to authenticate. Applying the bootstrap stack for an existing tenant — or adding the `GitHubActionsDeploy` statement by hand — fixes it, and the tenant page's **Test connection** button confirms it in seconds before anything is deployed.

### Verifying the setup before deploying

[`verify-tenant-aws.yml`](.github/workflows/verify-tenant-aws.yml) assumes the role, asks AWS who it is, and stops. It is read-only, takes seconds, and can be repeated freely. Critically it runs in the same GitHub environment a deploy runs in, so the token it presents carries exactly the subject a deploy would carry — a check that signed in any other way would report success for a tenant whose deploys all fail.

Nothing about the result is stored. The check describes the client's cloud at one moment, and a stored "Connected ✓" would age into a claim the platform cannot stand behind after a role is deleted or a trust policy edited.

### Required role name

The platform's own IAM identity (the principal shown above) is restricted by its own identity-based policy to only assume roles matching:

```
arn:aws:iam::*:role/chatbot-client-deploy-*
```

The client's role name **must start with `chatbot-client-deploy-`** (e.g. `chatbot-client-deploy-acme`) or onboarding's `AssumeRole` will be denied before the trust policy is even evaluated, regardless of how the trust policy itself is configured. The bootstrap template names the role for them, from the chatbot's slug.

This restriction now applies only to the onboarding path. Deploys federate directly and never pass through the platform's identity, so the prefix does not constrain them — but a role that breaks it cannot be onboarded in the first place.

## Azure Security Model

Figures: [before](docs/figures/fig-22-azure-credential-model-before.svg) · [after](docs/figures/fig-23-azure-credential-model-after.svg)

### How it works

The platform holds **no credential** for the client's Azure subscription. The client provides only identifiers: subscription ID, Entra tenant ID, and the client ID of a deployment identity (an app registration or a user-assigned managed identity). To that identity they add a [federated identity credential](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation) trusting GitHub Actions for one exact subject:

| Field | Value |
|---|---|
| Issuer | `https://token.actions.githubusercontent.com` |
| Audience | `api://AzureADTokenExchange` |
| Subject | `repo:<owner>/<repo>:environment:tenant-<tenant id>` |

The client creates that identity, its federated credential and its permissions in one step, from a **Deploy to Azure** link the wizard builds against [`infra/bootstrap/azure/tenant-bootstrap.json`](infra/bootstrap/azure/tenant-bootstrap.json). The wizard also shows the raw values and ready-made `az` commands for a client who would rather apply them by hand, and the tenant page shows them again afterwards. [`verify-tenant-azure.yml`](.github/workflows/verify-tenant-azure.yml) confirms the result — a read-only token exchange plus a check that the resource group exists — before any deploy is attempted.

On each deploy, `deploy-tenant-azure.yml` runs its job in the GitHub environment `tenant-<tenant id>`. GitHub signs an OIDC token whose `sub` claim names that environment. `azure/login` and the Terraform `azurerm` provider (`use_oidc = true`) exchange it with Entra ID for short-lived access tokens on the client's identity. The token exchange happens on the runner, and nothing reusable is created, stored or transmitted: not in the platform database, not as a workflow input, not as a GitHub secret.

The platform itself (the Next.js app) makes no Azure API calls at all.

### Why the subject names the tenant

A branch-based subject (`repo:<owner>/<repo>:ref:refs/heads/main`) would be identical for every customer. Any deploy run could then sign in to every subscription that trusts the platform, and an operator who entered another customer's client ID in the wizard would deploy into it. That is the Azure form of the confused-deputy problem ([Known Limitation #1](#1-no-externalid-on-aws-assumerole-should-be-added) describes the AWS form).

With the tenant in the subject, a customer's credential accepts only runs for their own tenant, and Entra ID rejects every other run before issuing a token. The tenant ID is a random UUID generated by the platform when the wizard opens, not the operator-chosen slug. Its primary-key uniqueness means no second tenant can claim it, including after a tenant is deleted.

This check is enforced by Microsoft Entra ID, which the platform does not control. The client can confirm it independently by listing their identity's federated credentials, and revoke access by deleting the credential.

### Where the trust moved

Removing the secret does not remove trust; it moves it from "whoever holds the secret" to "whoever can run this repository's deploy workflow for this environment". Concretely, anyone who can push workflow changes to the deploy branch, or dispatch the workflow, can deploy as any tenant whose subject they name. The controls for that boundary are GitHub's: branch protection on the deploy branch, a restricted set of repository collaborators, and the fine-grained `GITHUB_PAT` the platform dispatches with. See [Known Limitation #8](#8-the-deploy-repository-is-the-trust-anchor).

### Requirements

- **GitHub Environments.** The subject depends on the job's environment. Environments are available on public repositories, and on private repositories with GitHub Pro, Team or Enterprise. Without them the token carries a branch subject instead, Entra ID rejects it, and the deploy stops at the login step before creating anything. This fails closed.
- **Run length.** `az` cannot refresh a federated login, and the access token Entra issues lasts 60–90 minutes. The job's 45-minute timeout keeps the late `az` steps inside that window. Terraform is unaffected, since the provider requests a fresh GitHub token whenever it needs one.

### What the deployment identity can access

**Contributor and User Access Administrator, scoped to the chatbot's own resource group** — not to the subscription.

This is possible because [`infra/bootstrap/azure/tenant-bootstrap.json`](infra/bootstrap/azure/tenant-bootstrap.json) creates the resource group `chatbot-<slug>` itself, before creating the identity, and then confines both assignments to it. A role assignment cannot target a resource group that does not exist, so the group has to be created by the bootstrap for the scope to be narrowable at all. Terraform correspondingly *reads* the group rather than creating it (`data "azurerm_resource_group"` in `main.tf`).

The identity therefore cannot see, modify or delete anything else in the subscription.

Two roles rather than one, because Contributor cannot grant roles and the chatbot's runtime depends on granted roles — the container app pulls from its registry as itself, and the document-signing function reaches storage as itself. Terraform creates those assignments during a deploy. User Access Administrator is the one permission here that can widen access, which is why its scope matters more than any other: confined to this resource group, it can grant roles over the chatbot's own resources and nothing else.

Neither role can:

- Modify Microsoft Entra ID settings
- Grant itself anything outside the chatbot's resource group

A user-assigned managed identity is used rather than an app registration because creating one needs no permission in Entra ID, so a client can complete onboarding without involving a directory administrator.

### Teardown and revocation

`terraform destroy` (via [`destroy-tenant-azure.yml`](.github/workflows/destroy-tenant-azure.yml)) empties the resource group but deliberately leaves the group and the deployment identity standing — the job is signed in *as* that identity, so destroying it mid-run would fail the teardown, and it would take away the client's own revocation handle.

Deleting the resource group is that handle: it removes the identity, its federated credential and any remaining infrastructure together, and every subsequent deploy fails at the login step. The client does this themselves, in the portal, and the platform cannot prevent or undo it. Deleting only the federated credential revokes deployment access while leaving the running chatbot in place.

## Credentials in Transit

### GitHub Actions workflow dispatch

Secrets consumed by the workflows are sent over HTTPS. How they reach the workflow differs by cloud:

- **AWS** (`deploy-tenant.yml`) — neither the LLM key nor the customer's Pinecone key is passed to the workflow. Both are written to the tenant's Secrets Manager during onboarding; only their ARNs travel as inputs. Terraform needs the Pinecone value to create the index, so the workflow reads it back from the customer's own Secrets Manager under the assumed client role, `::add-mask::`es it, and hands it to the provider via `TF_VAR_pinecone_api_key`. With `vector_store = "pgvector"` no third-party key exists at all — the database password is generated by Terraform and never leaves the customer's account.
- **Azure** (`deploy-tenant-azure.yml`) — no Azure credential travels at all; the run signs in through federation (see [Azure Security Model](#azure-security-model)). The LLM key, the docs-signer secret and (for Pinecone tenants) the customer's Pinecone key cannot be pre-written into the customer's cloud as on AWS: Azure has no secret store at dispatch time, since Terraform creates the Key Vault, and the platform holds no Azure credential to create one. They are **not dispatch inputs**, which GitHub records in the run's event payload for anyone with read access to the repository. Instead the run fetches them from `POST /api/deployments/{id}/secrets` ([`src/lib/deploymentSecrets.ts`](src/lib/deploymentSecrets.ts)), authenticating with its own GitHub OIDC token. The platform releases them only when all of these hold:

  | Check | What it rules out |
  |---|---|
  | Signed by GitHub's issuer, for the audience `ai-chatbot-platform:tenant-secrets` | Forged tokens, and tokens minted to sign in to Azure (`api://AzureADTokenExchange`) or AWS (`sts.amazonaws.com`). Neither kind of token is accepted in the other's place |
  | `repository` is the platform's deploy repository | Any other repository, all of which can mint a token for the same audience. Checked before the database is touched |
  | `sub` is `repo:<owner>/<repo>:environment:tenant-<id>` for **this deployment's** tenant | Another tenant's run. This is the subject the customer's federated credential already trusts, so the secrets and the subscription are guarded by one binding |
  | `workflow_ref` is `deploy-tenant-azure.yml` (or `destroy-tenant-azure.yml` for a teardown) on the deploy ref | The connection check, which runs in the same environment, and a workflow edited on another branch |
  | The deployment is active, has not released its secrets before, and is not tied to a different run | Replay, and a second run racing the first. This check and the release are a single conditional `UPDATE` that sets `deployments.secrets_claimed_at` and pins `github_run_id` |

  A teardown receives only the Pinecone key, since destroying the index calls Pinecone's API. The workflow masks each value, writes it to a runner-temp file readable only by the runner user (never `$GITHUB_ENV`, which would hand it to every later step), sources that file in the Terraform steps only, and deletes it once Terraform is done. Terraform receives the values as `TF_VAR_*` environment variables rather than command-line arguments, since argv can leak into logs.

  **What remains:**
  - The values still reach the runner and Terraform state, as on any Terraform-managed secret (see [Known Limitation #9](#9-terraform-state-holds-tenant-credentials)).
  - Anyone who can change the deploy workflow on the deploy ref can still make it print them. That is [Known Limitation #8](#8-the-deploy-repository-is-the-trust-anchor), unchanged.
  - Secrets are released once. A GitHub "Re-run jobs" of a failed deploy is refused, and the operator redeploys from the platform instead.
  - GitHub-hosted runners must be able to reach `PLATFORM_BASE_URL`, which the status callbacks already require.

The platform-wide `PINECONE_API_KEY` GitHub repo secret is no longer used by either workflow: every tenant now brings their own Pinecone project or uses pgvector inside their own cloud.

Values referenced via `${{ secrets.* }}` are automatically masked by GitHub in all logs and the Actions UI. Secrets are still visible to GitHub as the service provider — an accepted limitation of the GitHub Actions model.

### Platform API surface

Credentials entered in the onboarding form are submitted over HTTPS to a Next.js Server Action. They are never echoed back to the client in API responses. The LLM API key field is rendered as `type="password"` with `autocomplete="off"`.

## Known Limitations

### 1. ~~No ExternalId on AWS AssumeRole~~ — resolved, then superseded

**Was:** `AssumeRole` was called with no `ExternalId`, so a client's role trusted the platform for every tenant. Anyone who could reach the onboarding form and knew a role ARN could have the platform provision into that account — the confused-deputy problem.

**Then:** every call sent a per-tenant `ExternalId` (the tenant's ID), and clients conditioned their trust policy on it. A tenant created against someone else's role sent a different value and was refused by STS.

**Now:** deploys and teardowns do not go through the platform's AWS account at all. They federate directly from GitHub into the client's account, on a subject that names the tenant's own environment (see [Why the subject names the tenant](#why-the-subject-names-the-tenant)), so there is no platform identity to confuse. The `ExternalId` survives on a second, narrower trust statement covering onboarding alone, which is the one operation GitHub cannot perform (see [Why the ExternalId still exists](#why-the-externalid-still-exists)).

Three limits worth stating:

- **It protects the client, not the platform's own operators.** Both conditions stop a *tenant* from borrowing another tenant's trust. Anyone who can run the deploy workflows can still name any tenant's environment — see [Known Limitation #8](#8-the-deploy-repository-is-the-trust-anchor).
- **It is only effective once the client applies it.** The platform cannot verify from the outside what a client's trust policy says; it can only observe that a sign-in worked. The **Test connection** check reports that much before a deploy is attempted.
- **The environment is load-bearing.** On a private repository without GitHub Pro, Team or Enterprise, no environment exists, no subject matches, and nothing deploys on either cloud. This fails closed, but it is a hard dependency on a paid GitHub plan.

### 2. ~~Azure client secret is decryptable by the platform operator~~ — resolved

**Was:** the customer's service-principal secret was stored AES-256-GCM encrypted, so anyone holding both the platform database and `PLATFORM_ENCRYPTION_KEY` could recover a credential that signs in to the customer's subscription, and it was resent as a workflow input on every deploy.

**Now:** Azure deploys use workload identity federation with a per-tenant subject (see [Azure Security Model](#azure-security-model)). No Azure secret exists to steal, the `azure_client_secret_encrypted` column is dropped (migration `0012`), and the secret is no longer a workflow input. The residual risk has moved to the deploy repository — see [Known Limitation #8](#8-the-deploy-repository-is-the-trust-anchor).

The LLM, Pinecone and docs-signer secrets are still stored encrypted and remain decryptable by the operator. They grant access to third-party services and to the docs-signer, not to the customer's cloud account.

### 3. Azure identifiers stored in plaintext

`azureSubscriptionId`, `azureTenantId`, and `azureClientId` are stored as plaintext. They are identifiers rather than credentials — with federation, knowing them grants nothing without a run whose token matches the customer's federated credential — but they do reveal which subscriptions the platform deploys into.

### 4. No per-deployment credential scope

The platform re-uses the same identity / role for every deployment of a given tenant. Credentials are short-lived on both clouds (a one-hour assumed role on AWS, per-run Entra tokens on Azure), but their permissions are the identity's full permissions, not scoped to the resources one run touches.

### 5. Azure pgvector server uses public networking

When a tenant selects the `pgvector` vector store on Azure, the PostgreSQL Flexible Server is created with `public_network_access_enabled = true`, fenced by the `allow-azure-services` (0.0.0.0) firewall rule rather than a private endpoint. This is *not* open to the public internet, but it does permit connections from any Azure tenant's resources that reach the server's hostname and hold valid credentials.

The reason is that Container Apps without VNet integration egress from rotating Azure IP ranges, so a narrow IP allow-list is not possible. The AWS equivalent has no such caveat: RDS is `publicly_accessible = false` with a security group admitting only the tenant's own ECS tasks.

**Planned mitigation:** Provision the Container Apps environment with VNet integration and move the server to a private endpoint (`public_network_access_enabled = false`), matching the AWS posture.

### 6. Pinecone indexes ignore the tenant's deployment region

The platform never passes `pinecone_environment`; it exists only as a Terraform variable defaulting to `us-east-1`, and the serverless `cloud` is hardcoded to `"aws"` in both configs. Every Pinecone index is therefore created in **AWS us-east-1** regardless of where the tenant's own infrastructure runs — including a tenant deployed to `eu-central-1`, or an Azure tenant in `westeurope`.

Data residency is consequently a property of choosing `pgvector`, not something a Pinecone tenant can control. A customer selecting Pinecone under a GDPR or data-locality requirement would not get what they expect.

**Planned mitigation:** Derive the index region from the tenant's own region via an explicit mapping, since Pinecone serverless supports only a subset of regions (AWS `us-east-1`, `us-west-2`, `eu-west-1`, `eu-central-1`, `ap-southeast-1`; GCP `us-central1`, `europe-west4`; Azure `eastus2`) — and Starter-plan projects are restricted to `us-east-1` entirely. The mapping needs a defined behaviour for regions with no Pinecone equivalent: reject at onboarding, or fall back with a visible warning on the form.

### 7. Any GitHub account may sign in

Access stops at authentication. Anyone who completes the GitHub OAuth flow reaches the dashboard and the onboarding form, and onboarding dispatches deployments and writes secrets into a customer's cloud account.

```
GitHub login → authenticated → platform
```

On a developer machine the exposure is nil, because nothing is reachable. It becomes the platform's weakest control the moment the control plane is hosted, and it is a deliberate scope decision rather than an oversight: the prototype's operator is also its only user.

**Available today:** `AUTH_ALLOWED_EMAILS` lists the accounts that may hold a session, matched on the email address of the GitHub account. Set, it is enforced as the session is created and again on every request that resolves one, so removing an address ends that operator's access on their next request (see [`src/lib/operators.ts`](src/lib/operators.ts)). It is a single environment variable, which is why it stays optional.

**Planned fix:** an approval step between authentication and access, so an account nobody invited lands in a pending state instead of the dashboard.

```
GitHub login → authenticated → invited or approved?
                                 yes → platform
                                 no  → pending / denied
```

That makes operator access data the platform owns rather than a string in its environment, which is what an environment variable cannot express: who invited whom, revocation as an event, and more than one level of access.

### 8. The deploy repository is the trust anchor

With no stored cloud credentials, what authorizes a deploy into a customer's cloud is a GitHub Actions run on this repository in environment `tenant-<id>`, which matches that tenant's own trust: the customer's IAM role on AWS, their federated credential on Azure. GitHub, as the token issuer, and anyone who controls the repository's workflows are therefore trusted.

- A collaborator with write access can change a workflow on the deploy branch, or dispatch one naming any tenant ID, and act in every customer account that trusts the platform.
- GitHub environments are created on first use by any workflow that names them, so the per-tenant subject separates tenants from **each other and from operators of the platform UI**, not from people who control the repository.
- `GITHUB_PAT` can dispatch those workflows.

**Mitigations in place:** OIDC trust bound to one repository and one environment per tenant, on both clouds; the platform's own GitHub role cannot assume any customer role; the platform dispatches only from its own validated inputs; no credential exists to exfiltrate from a run.

**Recommended:** protect the deploy branch (required reviews, no force pushes); pin third-party actions to commit SHAs, since `aws-actions/configure-aws-credentials` and `azure/login` handle the tokens; replace `GITHUB_PAT` with a GitHub App restricted to `actions: write` on this repository; keep the collaborator list to the operators who need it.

The same applies to the Azure application secrets: the platform releases them to a run on the deploy workflow in the tenant's environment (see [Credentials in Transit](#github-actions-workflow-dispatch)), so whoever controls that workflow's source controls what the run does with them. The release checks the repository by name, not by its immutable `repository_id`. A deleted repository whose name was later re-registered by someone else would therefore pass that check. Pinning `repository_id` closes this.

### 9. Terraform state holds tenant credentials

Terraform records in state every value it manages, and every credential a resource exposes, whether or not anything uses it. Where that state is kept therefore decides who else can read these values.

| Cloud | Where each tenant's state is kept |
|---|---|
| AWS | **In the customer's own account**, in `tfstate-<slug>-<account>-<region>-an`, a bucket their bootstrap stack creates. It sits in the account's regional namespace, so no other AWS account can register the name (the published "Bucket Monopoly" attack against names derived from an account ID and region does not apply). It is versioned, with superseded versions expiring after 30 days; private; TLS-only; and retained when the stack is deleted, so revoking access cannot fail on a non-empty bucket. The deploy and destroy workflows move a tenant's old state out of the platform's bucket on their next run, and refuse to continue on anything but a definite answer about where the state is ([`terraform-init-aws.sh`](.github/scripts/terraform-init-aws.sh)) |
| Azure | **In the customer's own subscription**, in storage account `cbtf<slug>` (container `tfstate`) inside the chatbot's resource group, created by their bootstrap. It accepts only Entra ID sign-in (Shared Key disabled). Terraform's backend reaches it with the run's GitHub OIDC token, and the deployment identity holds a data role on the state container only. It is versioned, with superseded versions expiring after 30 days, and locked with a blob lease per run. A storage account's name is global, so the workflows look the account up inside the tenant's own resource group before using it; an account of the same name in another tenant would also refuse this subscription's tokens. A name taken elsewhere can stop a deploy, but never receive state. The deploy and destroy workflows move a tenant's old state out of the platform's bucket on their next run, and refuse to continue on anything but a definite answer about where the state is ([`terraform-init-azure.sh`](.github/scripts/terraform-init-azure.sh)) |

The credentials in state:

| In state | Cloud | What it grants | Status |
|---|---|---|---|
| Docs storage account access keys | Azure | Read, list and change every document | **Unusable since this fix.** The account refuses Shared Key authorization (`shared_access_key_enabled = false`), and re-enabling it needs control-plane rights on the account, which state does not give |
| Docs-signer publishing credentials (`site_credential`) | Azure | Deploy code that runs as the docs-signer's identity, which can write and delete documents | **Unusable since this fix.** FTP and WebDeploy basic authentication are off; the workflow deploys with the run's federated identity |
| Function runtime storage account key | Azure | Replace the docs-signer's staged code package | Remains: a Linux Consumption plan needs it for host storage and zip deployment |
| LLM key, Pinecone key, docs-signer secret | Azure | The customer's LLM and Pinecone usage; writing and deleting documents through the docs-signer | Still in state, since Terraform writes them into Key Vault and the app settings, but that state is now kept in the customer's own subscription |
| Vector database password and URL | Both | Reading and changing the tenant's embeddings. Usable on Azure, whose server is reachable from any Azure-hosted client ([#5](#5-azure-pgvector-server-uses-public-networking)); on AWS the database is private | Still in state, now kept in the customer's own account or subscription |

AWS state holds no document credential: S3 has no account key, and the LLM, Pinecone and docs-signer secrets are written into the customer's Secrets Manager at onboarding, never through Terraform.

**What is left in the platform's hands:** nothing new. Every tenant's state is written only inside the customer's own cloud from now on. What remains is the old copies (below), and the fact that the deploy workflows handle state while they run, which is the repository trust anchor of [#8](#8-the-deploy-repository-is-the-trust-anchor).

**Historical exposure.** State written before these fixes still sits in the platform's bucket, including in older versions of each state object. For Azure it holds the keys and credentials above *in working form*; disabling Shared Key and basic authentication makes them unusable going forward. On both clouds the platform's copy stays behind after the move, superseded. Rotating what it held, and deleting the old objects and all their versions, removes it for good.

**Mitigation, in order:**
1. ~~Keep each AWS tenant's state in the customer's own account, locked~~ — done. Existing tenants move on their next run, once their bootstrap stack is updated.
2. ~~Keep each Azure tenant's state in the customer's own subscription, reached through Entra ID, locked~~ — done. Existing tenants move on their next run, once they have run their bootstrap again.
3. Rotate everything the old state held, after the move, so the new values exist only in the customer's state: both docs storage keys, the function runtime keys, the database passwords and the docs-signer secret. The customer rotates their own LLM and Pinecone keys with their providers.
4. Delete the old state objects, and every version of them, from the platform's bucket. Then remove the customer accounts' grants and the platform role's Azure-state grant on that bucket, and unset `LEGACY_STATE_BUCKET` in all four deploy and destroy workflows: the init scripts stop looking there. Do this only after confirming every tenant's state is in its own cloud, since a tenant still in the old bucket would otherwise start from empty state.

**Future work:** keep secrets out of state altogether. The options are an RDS-managed master password, Entra ID sign-in for Azure Postgres, Key Vault references for the application secrets, and write-only attributes (Terraform ≥ 1.11, azurerm 4.x).

### 10. The chatbot's public `/api/index`

The platform triggers indexing by calling `POST {chatbotUrl}/api/index` after every upload and delete. The load balancer routes all of `/api/*` publicly, so anyone who knows a chatbot's address can call it too, with no credential.

**Was:** the backend took the storage prefix from the request body. Indexing is a full resync that purges vectors for anything it does not find, so one anonymous request naming an empty prefix deleted a tenant's entire knowledge base. Concurrent requests also each ran a full re-embedding, so the endpoint could be used to keep the container busy.

**Now** (in `ai-chatbot/ai-backend`):
- **Nothing is taken from the caller.** The tenant, bucket and prefix all come from the container's environment. Emptying the index now requires actually deleting the documents, which only the docs-signer can do.
- **Requests merge.** One resync runs at a time per replica, with at most one queued behind it; any further request returns `202` at once. A flood costs at most two resyncs per replica.
- **Error responses no longer echo exception text** on either `/api/index` or `/api/ask`.

This protects a tenant only once it runs a chatbot image built after the fix. Tenants deployed from an older image remain exposed until they are redeployed.

**What remains:** the endpoint is still public. Anyone can make a tenant re-embed its own documents, bounded as above. It can no longer change or remove anything.

**Planned (indexing):** take indexing off the public surface entirely. Storage events inside the customer's cloud (S3 → SQS on AWS, Blob Storage → Event Grid → queue on Azure) would trigger indexing. `/api/index` would no longer be routed, and the platform would stop calling into the data plane for indexing at all.

### 11. ~~Terraform state is not locked~~ — resolved

Two Terraform runs against one tenant's state at once can corrupt it, for example a redeploy racing a teardown. **State is now locked on both clouds**, where it lives in the customer's own cloud ([#9](#9-terraform-state-holds-tenant-credentials)): every AWS run takes an S3 lock file (`use_lockfile`), and every Azure run takes a lease on the state blob. Both workflows pin Terraform 1.15.3. A lock also covers a Terraform run from outside the workflows, such as an operator's own machine. Before that, and still as a first line, two controls keep workflow runs from overlapping at all:

| Control | Where | What it stops |
|---|---|---|
| Unique index `deployments_one_active_per_tenant` | Platform database ([`schema.ts`](src/db/schema.ts)) | The platform dispatching a second deploy or teardown while one is pending or running, including two requests racing each other. The loser is refused before anything is dispatched or deleted |
| `concurrency: tenant-<id>`, never cancelling a running job | All four deploy and teardown workflows | Two runs for one tenant executing at once, including runs started by hand in GitHub. Later runs queue |

A deployment stuck as `running`, because its webhook was lost and nobody opened its page, blocks new ones until it is reconciled. Opening the tenant page does that: it reconciles from GitHub, and marks runs that cannot be found as failed after 75 minutes.

**What remains:** a tenant whose state has not moved yet is locked only once its next run has moved it, since the platform's old bucket was never configured for locking. That window closes with the move.

### 12. Azure uploads have no enforced size or type limit

Both docs-signers check the requested content type against an allow-list and the declared size against `MAX_UPLOAD_BYTES` (25 MB) before signing anything. What the storage service itself enforces afterwards differs by cloud:

| | AWS: S3 presigned POST | Azure: Blob user-delegation SAS |
|---|---|---|
| Size | `content-length-range` is a signed policy condition; S3 rejects a larger body | Not enforceable. A SAS has no size condition |
| Content type | `$Content-Type` is a signed condition; S3 rejects a different one | Not enforced. The SAS `contentType` field only sets the header returned on *download*, not a condition on upload |
| Object name | Fixed by the signed `key` condition | Fixed: the SAS names one blob |
| Lifetime | 60 seconds | 60 seconds |

On Azure, whoever holds a SAS URL can therefore upload any file of any type and size, up to Blob Storage's own per-request maximum, for 60 seconds. The URL is issued only to the tenant's owner after they sign in, and only for one blob name. So the realistic cases are an operator uploading something unintended, or someone intercepting the URL within its lifetime. The impact falls on the chatbot backend, which reads every blob when it indexes. An oversized file can exhaust the container's memory (1 GiB on Azure) during a resync, and a file of an unexpected type may be parsed as something it is not.

**Planned mitigation:**
- have the backend check each blob's size and content type before reading it, and skip or reject anything outside the same allow-list and limit;
- optionally have the platform check the blob's properties after upload through the docs-signer, and delete a non-conforming one.

S3 needs neither, since it enforces both at upload time.

### 13. The public chat endpoint has no rate or cost limit

`POST /api/ask` is intentionally public: it is the chatbot's end-user API, reached through the load balancer (AWS) or Container Apps ingress (Azure) with no authentication. Every request embeds the question on the container's CPU and makes one call to the LLM provider, **billed to the customer's own API key**. Nothing bounds that:

| Unbounded | Effect |
|---|---|
| Requests per client | No rate limit in the backend, no WAF rule on CloudFront or the ALB, and Azure Container Apps has no built-in throttling. A script can call it continuously |
| `top_k` (caller-supplied) | Controls how many chunks can enter the prompt. A large value, filtered only by the relevance floor, can put much of the knowledge base into a single request |
| Question length | Unbounded, and sent to the model in full |
| Reply length | No `max_tokens` is set on the completion |

The result is **cost abuse against the customer**, bounded only by their provider's own spending limits, and some CPU load on the container. It does not expose other tenants or the platform: each chatbot is isolated in its customer's account with its own key.

**Planned mitigation, cheapest first:**
- bound `top_k` (e.g. 1–10), question length and `max_tokens` in the request model and the completion call;
- add a per-client rate limit in the backend, which covers both clouds identically;
- on AWS, add a WAF rate-based rule on the CloudFront distribution or ALB.

Customers should also set a spending limit with their LLM provider. The deployment guide should say so, whatever the platform enforces.

## Platform Operator Responsibilities

The following must be secured by the platform operator:

| Secret | Where set | Risk if exposed |
|---|---|---|
| `PLATFORM_ENCRYPTION_KEY` | Server environment variable | Stored LLM, Pinecone and docs-signer secrets become decryptable (no cloud credential is stored) |
| `GITHUB_PAT` | Server environment variable | Attacker can trigger arbitrary workflow dispatches, and so deploy as any tenant (see [Known Limitation #8](#8-the-deploy-repository-is-the-trust-anchor)) |
| Operator's AWS sign-in session (`aws login`) | AWS CLI login cache on the platform's machine, reached by the application through `AWS_PROFILE` | Attacker can assume every customer's `chatbot-client-deploy-*` role until the session expires |
| `DEPLOY_WEBHOOK_SECRET` (server) / `PLATFORM_WEBHOOK_SECRET` (GitHub Actions) | Server env + GitHub Actions secret | Attacker can report a false outcome for a deployment still in progress. They cannot reopen a finished deployment, and cannot redirect a tenant's docs-signer URL (see below) |
| `TF_STATE_BUCKET` | GitHub Actions secret | Reveals Terraform state storage location |

These values must never be committed to source control, logged, or included in error responses.

**What the status webhook can change.** One shared secret authenticates every run's callbacks, so the webhook ([`status/route.ts`](src/app/api/deployments/[id]/status/route.ts)) limits what a callback may do rather than trusting it:

- **A deployment only moves forward.** Callbacks are accepted only while a deployment is `pending` or `running`. No callback can set `pending`, and a finished deployment cannot be reopened or rewritten. The write itself re-checks the status, so a late callback and the lost-webhook reconciliation cannot overwrite each other.
- **The docs-signer URL must be the tenant's own** ([`acceptDocsSignerUrl`](src/lib/docsSigner.ts)). The platform sends the tenant's docs-signer secret to that URL, so an unchecked value would let whoever holds the webhook secret collect every tenant's docs-signer secret. On Azure the URL is fully determined by the slug and must match exactly. On AWS the Function URL's ID is random, so the check covers the shape (`https://<id>.lambda-url.<tenant region>.on.aws/`), and the first URL recorded is **pinned**: a later callback cannot replace it. The same check applies to URLs recovered from the run artifact, and again immediately before every call that sends the secret.

**Residual:** on AWS, the pin trusts the first callback. Someone holding the webhook secret during a tenant's very first deploy could race the real callback with their own Lambda URL in the same region; the next document upload would then send the secret there. **Planned:** stop sending the secret at all. The platform would sign each request with an HMAC keyed by the secret, and the signer would verify it, so a redirected URL receives nothing usable. That needs a change to both signer functions and a redeploy of every tenant.

**Who may sign in.** Anyone who completes the GitHub OAuth flow, unless `AUTH_ALLOWED_EMAILS` narrows it to named accounts — see [Known Limitation #7](#7-any-github-account-may-sign-in). Either way the request proxy requires a session for every route except the sign-in page and the deployment webhook, which authenticates its own header. That holds because [`src/auth.ts`](src/auth.ts) supplies an `authorized` callback: `next-auth` authorizes every request when one is absent.

**GitHub Actions holds no AWS key.** Deploy and teardown workflows sign in to each customer's role directly with the run's own OIDC token (see [AWS Security Model](#aws-security-model)). The one platform credential they use is the role in [`infra/platform/github-oidc`](infra/platform/github-oidc), for pulling the golden images and, while old state is being moved, reading an Azure tenant's old state. Nothing reusable is stored, and each customer-role session is named after the workflow run that opened it, so a customer's CloudTrail ties every action to one run.

That role trusts jobs of this repository running in any `tenant-*` environment. It is a wildcard, and the branch cannot be checked beside it: AWS evaluates only a GitHub token's `sub` and `aud`, and a job running in an environment carries the environment in `sub` instead of the branch. What bounds it is the role's permissions. It holds no `sts:AssumeRole`, so it cannot reach any customer's account. The remaining exposure is the old Azure state: until it is deleted ([#9](#9-terraform-state-holds-tenant-credentials), step 4), a workflow on any branch that names a `tenant-*` environment can read it. Deleting the old state, and the grant with it, removes that.

**Nor any Azure credential.** Azure deploys sign in through the customer's federated credential, which trusts the run's own GitHub OIDC token for that tenant's environment. The application makes no Azure calls at all.

**Neither does the application.** It assumes the `platform-control-plane` role defined in [`infra/platform/control-plane`](infra/platform/control-plane) from the operator's `aws login` session, and that role may do one thing: `sts:AssumeRole` into `chatbot-client-deploy-*` roles. Two independent checks keep a stored key from standing in for the session. `assumeTenantRole` refuses credentials without a session token before signing anything, and the role's trust policy admits only temporary credentials. On a host that signs its own OIDC token, `PLATFORM_AWS_ROLE_ARN` makes the application exchange that token for the same role instead, with no session and no human in the loop; the trust policy admits one named project environment, so a preview deployment of a branch cannot use it. `GITHUB_PAT` remains long-lived; it could become a GitHub App's short-lived installation tokens.

## Client Security Checklist

### AWS
- [ ] Create a dedicated IAM role used only for this platform, named `chatbot-client-deploy-<something>` (see "Required role name" above)
- [ ] Scope the role's permission policy to the minimum required — no minimal policy is published yet; the role needs to create VPC/networking, ALB, ECS, ECR, S3, Secrets Manager, CloudWatch Logs, IAM roles for the ECS tasks, and (if using pgvector) RDS resources, per [`infra/terraform/main.tf`](infra/terraform/main.tf)
- [ ] Add the `sts:ExternalId` condition shown by the onboarding wizard to the role's trust policy, **before** submitting the form — without it the role can be assumed for any chatbot, not just yours
- [ ] Enable CloudTrail in the deployment region to independently audit all platform activity
- [ ] Review and revoke the role if the tenant is deleted

### Azure
- [ ] Create a dedicated deployment identity (app registration or user-assigned managed identity) used only for this platform — **do not create a client secret for it**
- [ ] Assign Contributor and User Access Administrator at the **subscription** scope (Terraform creates the resource group and the chatbot's narrow role assignments itself, so scoping to a not-yet-existing resource group will fail — see "What the deployment identity can access" above and step 4 of [`CLIENT-DEPLOYMENT-GUIDE.md`](CLIENT-DEPLOYMENT-GUIDE.md))
- [ ] Add the federated credential exactly as the onboarding wizard shows it — subject `repo:<owner>/<repo>:environment:tenant-<tenant id>`, never a branch subject, which would trust every tenant's deploys
- [ ] Use a separate identity per tenant (not one shared across all tenants)
- [ ] Delete the federated credential (revokes the platform immediately) and the identity when the tenant is no longer needed

### Both clouds
- [ ] Use a dedicated LLM API key for each tenant rather than a shared organization key
- [ ] Set spending limits on the LLM API key if the provider supports it. The chatbot's chat endpoint is public and not rate-limited, so this is the only cap on what anonymous traffic can cost you (see [Known Limitation #13](#13-the-public-chat-endpoint-has-no-rate-or-cost-limit))
- [ ] Review the platform's open-source code before onboarding sensitive workloads
